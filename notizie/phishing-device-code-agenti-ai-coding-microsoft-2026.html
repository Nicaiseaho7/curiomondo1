Microsoft testa il phishing con device code contro agenti di programmazione AI

Una pagina GitHub autentica può autorizzare il client sbagliato: la simulazione mostra l’impatto possibile su repository, sessioni e memoria.

Una richiesta di accesso aperta sul sito autentico di GitHub può diventare il passaggio centrale di un attacco di phishing con device code. Microsoft ha simulato il meccanismo con GitHub Copilot CLI per mostrare come un’autorizzazione concessa al client avviato dall’attaccante possa estendersi agli strumenti e alle risorse accessibili dall’identità della vittima.

Nel flusso OAuth per dispositivi, un client ottiene un codice breve e l’utente lo inserisce nella pagina di verifica. Nell’attacco, è l’aggressore ad avviare la richiesta e a convincere la persona a usare il codice, magari fingendo un controllo IT o una licenza. Il dominio è corretto, ma l’iniziatore non lo è.

Dopo l’approvazione, il client controllato dall’attaccante completa l’accesso. Nel laboratorio Microsoft, i possibili effetti dipendevano dai permessi e dalle funzioni abilitate: accesso ai repository privati, lettura di sessioni sincronizzate, inserimento di informazioni fuorvianti nella memoria e interazione con una sessione remota già attiva e configurata per il controllo.

Microsoft sottolinea che questi quattro esiti sono una dimostrazione controllata e non sono stati osservati nelle campagne citate. Non si tratta di esecuzione remota senza autenticazione: il controllo remoto richiede una sessione online, la funzione abilitata e i relativi permessi. Anche l’accesso ai repository resta limitato alle autorizzazioni dell’account compromesso.

L’azienda ha preparato due rilevazioni Defender che correlano messaggi o clic sospetti con la creazione o rigenerazione di token GitHub, una per email e una per Teams. Per gli utenti GitHub Enterprise Managed Users ha inoltre testato la sospensione dell’identità tramite il provider aziendale, nelle configurazioni che supportano telemetria e integrazione richieste.

La difesa più immediata è approvare soltanto codici generati da un accesso iniziato personalmente. Le organizzazioni possono limitare ruoli e archiviazione delle sessioni, rivedere applicazioni OAuth e memorie salvate, e revocare autorizzazioni inattese. Una pagina legittima conferma il servizio che riceve il codice, non l’identità di chi ha avviato la richiesta.
